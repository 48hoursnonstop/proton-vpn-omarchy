# 0.9.6-rc4 — Motion and continuous traffic history

This local frontend candidate refines transitions and makes traffic collection
independent of the current page. Backend packaging remains pinned to the signed
`v0.9.6-rc1` release. No authentication, keyring format, namespace or migration
logic changes. `AgentState.qml` adds only the collector and its client version;
installer/uninstaller sources and verification metadata are unchanged.

## Motion

Omarchy already provides a 140ms OutCubic panel fade, 120ms button fills and
120ms switch movement/color transitions. RC4 adds a 120ms OutCubic settling fade
for subsequent page changes, a reversible disclosure-chevron rotation, and
opacity transitions for disabled buttons and search progress.

The destination is loaded and interactive immediately. Rapid navigation continues
from the current opacity instead of flashing or queuing transitions. There is no
initial page entrance or hidden-window page animation. The plugin's existing
inline settings object accepts `reducedMotion: true` to make these added
transitions immediate; native Omarchy host/control animations remain owned by
the shell toolkit.

The status mark keeps its existing appearance and immediate state changes. Its
redundant hidden image layer was removed after render comparisons isolated a
missing-logo regression when the workspace gained opacity animation. The image
itself supplies the texture to MultiEffect, as supported by the
[Qt MultiEffect documentation](https://doc.qt.io/qt-6/qml-qtquick-effects-multieffect.html).

## What the graph records

Previously each traffic card owned its timer and 45-element arrays. A closed
native host probe with synthetic state produced three requests on Home, no
additional requests on Settings, then three more after returning to Home.
Window visibility did not reliably stop the card's timer. Recreating the page
discarded its arrays, and the chart stretched whatever samples existed across
the full width.

RC4 owns one `ProtonTrafficHistory` per agent adapter:

- Poll the existing local `traffic.get` once per second while connected and the
  agent is available; retain the adapter's pending-request guard.
- Keep at most 300 timestamped points covering five minutes, only in RAM.
- Share those points between Home and Connection details, including after those
  views are destroyed and recreated. No view starts its own polling timer.
- Stop polling when disconnected or the agent is unavailable. Disconnect,
  server/protocol changes and counter resets start a fresh history.
- Rebase after gaps over 2.5 seconds, clock reversal or unavailable samples.
  Draw missing observations as gaps instead of zeroes or a misleading average
  speed after suspension.
- Paint only a visible card in a visible window. Map timestamps to a fixed
  five-minute horizontal axis; use a labeled power-of-two vertical scale to
  avoid changing the scale for every small new peak. Download is solid and
  upload dashed. EN/ES captions identify the time window and rate ceiling.

The native backend reads RX/TX totals from the `proton0` interface's kernel
counters and calculates rates between observations. Those counters accumulate
while the interface exists, independently of the panel. They are interface
totals, not a permanent usage ledger. The new historical rate samples exist only
while this Omarchy frontend/adapter is running: restarting the shell, reloading
the plugin or removing the widget discards them. There is no disk log or new
backend daemon. Continuing history across frontend restarts would require a
separate backend-history feature and is outside this candidate.

Mode: full within the changed motion, traffic lifecycle and graph presentation.
Framework: Qt Quick/QML, Quickshell and the existing `qs.Commons`/`qs.Ui` toolkit.
Applied skills: make-interfaces-feel-better, better-ui and Omarchy integration.

| Category | Evidence inspected | Result |

### Considered but rejected

| Location | Candidate | Rejected because |
| --- | --- | --- |
| Routes and frequent controls | Spring scaling, staggered tab contents or blocking exit sequences | Existing Omarchy motion is brief; repeated navigation should remain immediately usable |
| Traffic history | Write every observation to disk or add a second service | A bounded live graph needs a rolling RAM buffer; durable accounting is a separate product feature |
| Traffic graph | Smooth/interpolate all samples and fill across outages | This could disguise observation gaps and change the apparent shape of measured traffic |


The runtime suite includes new traffic-history and motion fixtures. Traffic tests
cover collecting before a view exists, one collector with two views, hidden and
destroyed views, reopening with existing points, agent unavailability,
disconnect, more than ten minutes of samples, suspension gaps, recovery,
counter/server resets and unknown data. Existing passive-error isolation and
traffic rendering tests remain passing. Motion tests check intermediate frames,
rapid route changes, reversed rotation, settled values and reduced motion.

All UI tests use synthetic state. The RC3 lifecycle probe used the native
Wayland host while closed; image captures and interaction windows use offscreen
FloatingWindow instances. Nineteen production route-entry captures were refreshed
with a synthetic populated traffic history. Final visual inspection includes
Home in native themes and 320px Spanish Home. No preview was tiled.

Not verified: 10% speed replay, physical GPU frame-time profiling, full-duration
live VPN traffic sampling, cross-monitor frontend instances or screen-reader
announcements. Backend source was inspected read-only; live authentication and
VPN mutation were not needed for these UI fixtures.

Verdict: **Approve for local RC evaluation within the inspected scope**, with
the unverified checks above. This candidate has not been published to GitHub.
